UI Fidelity QA Framework

An automated way to check that the live website matches the Figma design. It measures both, compares them value by value, and tells us exactly what to fix.

Why we built it

Manual design QA

  • Figma on one screen, website on the other
  • Zoom, inspect, compare by eye
  • Small things slip through: a 6px gap, #1B6AAA instead of #155791
  • Two testers can reach two different answers
  • Everything is repeated after each fix

With the framework

  • Exact values are read from the design and the page
  • Hundreds of checks per page in one run
  • The same rules every time
  • Each difference comes with the expected value, the actual value and the fix
  • Rerun after a fix to confirm it

How it works

Figma designframe exported as SVG
Live websiteopened at the same width
Measureexact values read from both sides
Comparefixed rules, same every run
Reportone page per screen: scores and fixes

  1. Read the design

    The Figma frame is exported as SVG. That file keeps the layer names, colours, fonts, sizes and positions, so each element can be measured exactly.

  2. Read the website

    Playwright opens the live page in a real browser at the same width, waits for fonts and images, and reads the values the browser actually uses. These are the same values you see in DevTools under Computed.

  3. Compare and report

    Each pair of values is checked with fixed rules. The report lists what matches, what differs, what must change, and a score.

Think of it as a tester with Figma Inspect on one screen and DevTools on the other, checking every value. It checks hundreds of them per page and never applies the rules differently.

The five audits

Every page gets five audits. Each one measures Figma, measures the website, then compares them. Audits A to D follow our 12 design-audit prompts (A1 to D3); audit E checks every text block on the page.

A

Style guide

Colours, fonts (family, size, weight, line height, letter spacing), borders, corner radius, shadows and gradients.

Footer brand bar colour: Figma #155791, website #1B6AAA

B

Layout

Page and container widths, grid columns, element sizes and positions, spacing between sections, padding inside cards.

Footer height: Figma 551px, website 668px

C

Responsive

Loads the page at 7 widths (375, 768, 1023, 1024, 1279, 1280, 1440), saves a screenshot at each, and records what changes.

Partner card grid at 1440: Figma 3 columns, website 4 columns

D

Component states

Buttons and links in default, hover, focus, focus-visible and active states, the same way DevTools forces them.

Nav link label: Figma "About Us", website "About"

E

Text

Finds every Figma text on the live page by its words, then compares wording, font, size, weight, colour and number of lines.

Footer link: Figma "Partner Opportunity", website "Partner Opportunities"

?

What each audit needs

A to D need the page's element map and check list. E needs only the page path and its Figma SVG, so it runs on any new page straight away.

All examples above are real findings from the 4 Nov run.

Why 1023 and 1024, 1279 and 1280? Those pairs sit on either side of the two widths where the site's layout switches. It is boundary value testing applied to breakpoints.

How to read a result

✓ Match

Both values exist and are equal under the rules below.

✗ Different

Both values exist and they differ. Comes with the fix.

? Could not verify

One side has no value. The tool never guesses and says why.

  • Under 1px counts as a match.
  • Same colour, different notation counts as a match: #FFF = #FFFFFF = rgb(255, 255, 255).
  • Major: colour, font family or weight, structure (columns, visibility, wrapping, labels), wording, and gaps of 8px or more. Minor: everything else, including punctuation-only text differences.
  • Confidence High when both values are read directly; Med when one is derived or a text was matched by similar wording, and the row says why.
  • Score = matched ÷ (matched + different). "Could not verify" items are left out of the score.

The report

Open reports/index.html. It lists every page with its five scores. Each page has one report.html:

  • Scores: one card per audit and a total, with the number of differences and how many are Major.
  • Fix first: the 10 most important differences across all five audits.
  • Every check: a table you can filter by result, audit, severity or search. Each difference has a Copy for bug button with the element, expected and actual values, and the fix.
  • Screenshots from audit C at every width.
  • Details: the full report each audit prompt asks for, as Markdown, in reports/<page>/details/.

How QA uses it

  1. Run the audits

    One command for every page, or one page or audit at a time.

  2. Open the report

    reports/index.html, then the page. Start with Fix first.

  3. Triage

    Filter to Major. Every row already has the Figma value, the website value and the fix.

  4. Check the rest by hand

    Switch the filter to "Could not verify". Each row says why and names the selector to inspect in DevTools.

  5. Log bugs

    Use Copy for bug and paste it into the ticket.

  6. Rerun after the fix

    The item moves to Match and the score goes up.

Run it yourself

From the project folder, after npm ci and npx playwright install chromium:

npx playwright test               # all five audits, every page (same as: npm test)
npx playwright test -g home       # one page: home, partner-opportunity
npx playwright test e-text        # one audit: a-style, b-layout, c-responsive, d-component, e-text

Then open reports/index.html.

Testing another build, such as the internal server

$env:BASE_URL = 'http://192.168.5.250:8081'; npx playwright test   # PowerShell
Remove-Item Env:BASE_URL                                            # back to production

GitHub Actions runs the audits on every push and pull request to main and keeps reports/ as the ui-fidelity-reports download for 30 days.

Add a page

  1. Export the design

    Export the Figma frame as SVG with Outline text off, and save it as design/<name>-1440.svg.

  2. Describe the page

    Create pages/<name>.js with four fields:

    module.exports = { name: 'about', title: 'About', path: '/about', svg: 'about-1440.svg' };

  3. Add it to the list

    Add require('./about') to pages/index.js. Audit E runs on the next run.

  4. For audits A–D

    Copy pages/home.js and home.checks.js, then change the selectors and checks. Until then, A–D are skipped with the reason shown.

What it does not do yet

  • It runs in Chrome only, because forcing hover, focus and active uses Chrome DevTools.
  • Figma has only the 1440 desktop frame, so other widths go to "Could not verify" until tablet and mobile frames are added.
  • Icons and text drawn as images have no CSS colour or text, so they are not compared.
  • A text reworded by more than about 30% cannot be matched with confidence and goes to "Could not verify".
  • Hover and focus effects that come from a parent element (:focus-within, group hover) are not forced.
  • If developers change the page markup, the affected checks move to "Could not verify" and name the selector that stopped matching. They do not fail silently.
  • It compares measurable values. Image quality and animation still need a human eye.

Glossary

Playwright
A browser automation tool. It opens pages and reads values the way a tester would.
SVG export
The Figma frame saved as a file that keeps layer names, colours and text.
Computed CSS
The final style values the browser applies. DevTools › Elements › Computed.
Viewport
The browser window width the page is tested at, for example 1440px.
Selector
The address used to find an element on the page, for example header nav a.
Soft assertion
A check that records a failure and keeps going, so one run lists every difference.
BASE_URL
The site the audits test. Unset means production.
Element map
The list in a page file that pairs each Figma layer with its element on the live page.
